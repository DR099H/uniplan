Проект разрабатывается командой в соответствии с практической работой №2 «Планирование командной разработки: декомпозиция, бэклог, спринты и риски».

## 2. Модель ветвления (GitFlow / GitHub Flow)

* Ветка `main` является стабильной и защищённой. Прямые коммиты в `main` запрещены.
* Для каждой пользовательской истории (`US-xx`) или технической задачи (`TSK-xx`, `TST-xx`, `BUG-xx`) создаётся отдельная ветка:
  * `feat/<ID-задачи>-<краткое-название>` — новая функциональность;
  * `fix/<ID-задачи>-<краткое-название>` — исправление дефектов;
  * `docs/<ID-задачи>-<краткое-название>` — документация и спецификации;
  * `test/<ID-задачи>-<краткое-название>` — автотесты;
  * `perf/<ID-задачи>-<краткое-название>` — оптимизация и производительность.

## 3. Процесс слияния (Pull Requests)

1. Разработчик завершает работу в ветке и создаёт Pull Request в `main`.
2. Обязателен прогон автотестов (`npm test`) — все 27 тестов должны завершаться успешно.
3. Проводится ревью кода (Code Review) минимум одним участником команды.
4. Слияние выполняется с сохранением истории (`git merge --no-ff`) для наглядности в графе сети GitHub (Network Graph).

## 4. Соглашение об именовании коммитов (Conventional Commits)

Формат сообщений коммитов:
```
<тип>(<задача>): <краткое описание на английском или русском>
```

Примеры:
* `feat(US-02): implement week calculation algorithm and schedule API endpoint`
* `fix(BUG-01): fix semester start week parity calculation across New Year boundary`
* `test(TST-01): add automated unit and integration tests for US-01..US-03`
* `docs(TSK-04): specify REST API contract and schedule JSON schema`
