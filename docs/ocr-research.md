# RSR-01: Исследование технологий оптического распознавания текста (OCR) для расписания занятий

* **Исполнитель**: Сабанчеев Р. М. (QA Engineer / System Analyst)
* **Статус**: Выполнено (Спринт 2)
* **Цель**: Исследовать возможность автоматического импорта расписания занятий из фотографий и сканов бумажных стендов / скриншотов Word/Excel таблиц.

---

## 1. Контекст и проблематика
Студенты и старосты часто получают расписание в виде скриншотов мессенджеров, фотографий распечаток со стенда деканата или неструктурированных таблиц. Ручной перенос пар трудоёмок. Рассматривалась реализация пользовательской истории `US-06` (Автоматическое распознавание расписания по фото).

---

## 2. Сравнительный анализ решений

| Решение | Преимущества | Недостатки | Вывод |
|---|---|---|---|
| **Tesseract.js** (Client-side WASM) | Работает прямо в браузере, нулевая нагрузка на сервер, приватность данных | Большой вес модели (~15-20 МБ), низкая точность на сложных границах таблиц, частые ошибки в номерах аудиторий и фамилиях | Непригодно для стабильного MVP |
| **Cloud OCR (Yandex Vision / Google Cloud Vision API)** | Высокая точность (>95%), хорошая детекция табличных структур | Платный сервис, зависимость от внешнего провайдера и сети, необходимость безопасного хранения API-ключей | Возможно в качестве опционального плагина в версии 2.0 |
| **PaddleOCR / DocTR** (Python backend) | Отличная точность распознавания табличных ячеек | Требует отдельного сервера с GPU/CPU ML-инференсом, не вписывается в архитектуру лёгкого SPA/Node.js/PHP хостинга | Избыточно для базового студенческого решения |

---

## 3. Анализ рисков распознавания табличных данных
Таблицы расписания вуза имеют специфические особенности:
1. Объединённые ячейки по чётным/нечётным неделям (I / II неделя).
2. Дроби в номерах аудиторий (`7-414`, `1-118`).
3. Сокращения предметов и типы пар (`лекция`, `лаб.`, `пр.`).

Ошибка OCR хотя бы в одном символе (например, перепутать аудиторию или неделю) приводит к дезинформации студентов.

## 4. Итоговое архитектурное решение команды
1. **Для версии 1.0 (MVP)**:
   - В качестве надёжного и детерминированного способа импорта утверждён **структурированный JSON-формат** (`US-05`) с предпросмотром, валидацией схемы и проверкой коллизий расписания.
   - Подготовлены открытая спецификация формата ([api-contract.md](api-contract.md)) и шаблон файла ([schedule-template.json](schedule-template.json)).
2. **Для версии 2.0 (Post-MVP Backlog)**:
   - Модуль OCR вынесен в отдельный бэклог будущих версий с возможностью гибридного сценария (OCR распознаёт черновик в JSON с обязательным ручным подтверждением старостой в UI перед сохранением).
